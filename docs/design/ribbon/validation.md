# 리본 검증 기록

## 재생부

`tests/fixtures/pastel-intro.html`은 Vite 개발 서버에서만 여는 기능 검증 화면이다. 번호를 그린 합성 프레임을 사용하므로 리본의 형태나 움직임 품질을 증명하지 않는다. `realLoader=1`은 실제 WebP 변환과 브라우저 이미지 디코더를 사용한다.

IAB에서 다음 동작을 확인했다.

| 시나리오 | 확인한 결과 |
| --- | --- |
| 실제 WebP 디코딩 | 0–11번을 중복·누락 없이 표시. 1–11번 표시 간격 합계 약 340ms. |
| 프레임당 120ms 디코딩 | 중간 모양을 생략하지 않고 순서대로 재생. |
| 마지막 프레임 | 마지막 투명 프레임 표시 후 약 311ms 뒤 패널 개방 시작. |
| 이미지 준비 실패 | 종료 콜백 1회, 커버 제거, 스크롤 잠금 해제. |
| 로딩 중 건너뛰기 | 이미지를 그리지 않고 종료 콜백 1회, 커버와 잠금 제거. |
| 자산 준비 시간 초과 | 약 5초 뒤 본문 접근 복원. |
| 재생 중 디코딩 실패 | 패널 동작을 시작하지 않고 본문 접근 복원. |
| 다음 프레임 정지 | 약 1.5초의 프레임 대기 제한 뒤 본문 접근 복원. |

정상 종료 시 패널의 최종 computed transform, 투명한 커버 배경, 종료 후 커버 부재와 스크롤 잠금 해제를 별도로 읽었다. 단위 테스트 12개도 통과했다.

추가 독립 검토에서 디코딩 도중 취소한 비트맵을 늦게 받더라도 한 번 해제하고, 취소 후 요청은 `AbortError`로 거부하는 것을 확인했다. 새 차단 결함은 발견하지 못했다. 실제 리본 자산의 성능이나 공개 페이지 통합 검증을 대신하는 결과는 아니다.

`scripts/ribbon/package_sequence.py`는 고정 크기 PNG를 무손실 WebP로 변환하고, 첫 프레임의 가시성과 마지막 프레임의 완전 투명, 4MiB 용량 제한을 확인한다. 기존 v4의 46장으로 도구를 실행해 RGBA 전체 바이트 동일성과 정상 종료를 확인했다. 변환 결과는 3,944,384바이트이며 기존 v4 출력과 별도 산출물이다. IAB에서 생성된 검토 화면의 로드와 0.25배속 재생 종료도 확인했다. 이는 변환기 검증이며 v4 동작의 미통과 판정을 바꾸지 않는다.

## 3D 샘플 v4: 미통과

고정 카메라의 46프레임을 출력했고, PNG와 WebP의 알파 바이트 동일성 및 마지막 프레임의 완전 투명을 확인했다. 전체 WebP는 3,944,120바이트다. 원본 `.blend`는 각 표면의 형태 키를 포함해 제작 스크립트 없이 재생된다.

독립 시각 검증에서는 19–34번 프레임을 연속 판독해 미통과로 판정했다. 24–28번에서 고리가 매듭을 통과하지 않고 수평 조각으로 변하며, 27–31번에 앞뒤 띠의 이중 윤곽과 접합선이 남는다. IAB의 390px 저속 재생 화면에서도 해당 구간을 확인했다. 여섯 독립 표면을 포개는 표현 방식이 원인이다.

이 샘플은 공개 자산으로 복사하거나 앱에 연결하지 않았다. 다음 제작 방식은 하나로 연결된 띠의 재료 경로와 매듭 통과를 먼저 검증해야 한다.

## 단일 띠 진단 v5: 미통과

여섯 표면을 포개는 방식을 폐기하고, 고정된 재료 좌표를 가진 연결 메시 1개(정점 9,909개)로 재설계했다. 두 번째 검사의 0/12/20/23/28/36번 프레임에서 교차 삼각형 쌍은 각각 477/491/439/410/355/464개였다. 이는 물리적 충돌 사건 수가 아니다.

첫 시도의 고정 소스로 별도 QA를 수행해 보고된 삼각형 세 쌍의 실제 내부 관통을 독립 계산으로 재현했다. 단순 끝점 접촉이나 인접 면을 관통으로 잘못 센 것만으로 실패가 발생한 것은 아니다. 두 번째 소스의 수치를 첫 시도 재현 결과와 혼합하지 않았다.

전체 중심선 길이는 대략 유지했지만 각 재료 구간의 비신축성, 충돌 없는 매듭 통과와 프레임 사이 접촉을 증명하지 못했다. 따라서 재질 렌더와 공개 자산 생성을 진행하지 않았다. 이는 현재 저작 방식이 수용 조건에 도달하지 못했다는 결과이며, 해당 동작이 물리적으로 불가능하다는 뜻은 아니다.

이후 아래의 연결된 매듭 경로 방식으로 제작을 계속했다. 기존 정지 포즈를 추가 생성하거나 타이밍만 바꾸는 것으로 이 조건을 대체하지 않았다.

## 최종 연결 리본 샘플: 통과

CC0 매듭 중심선을 출발점으로 폭이 있는 하나의 연결 표면을 만들고, 고리 축소에 따라 꼬리로 길이를 보내는 경로를 직접 작성했다. 꼬리의 위·바깥 이동, 끝단의 매듭 통과, 풀린 띠의 처짐과 낙하를 46개의 형태 키로 저장했다. 실제 천의 접촉을 계산하는 물리 시뮬레이션은 아니다.

- 고정 원본 SHA-256: `e7ea7ce16272f8a2b06be518ad72ca75bacc36845aa9fbc2d7ba898b0f6649b8`.
- Blender 4.5.13, Cycles CPU 16 samples, 고정 직교 카메라 배율 9.5, 960×640, 30fps. 렌더 프로세스 exit 0.
- 부모 IAB 검토: 390px 정상 속도와 768px 0.25배속에서 고리 축소, 매듭 해제, 띠 퇴장이 이어짐을 확인했다.
- 독립 픽셀 검토: 0–39번 연속 비교와 20–39번 중앙 확대에서 명백한 순간 고리 소멸, 크기 튐, 분리 조각, 보이는 관통이 없었다. 20–31번의 평행 윤곽은 꼬리와 가로 띠의 겹침으로 추적됐다.
- 28–30번 자유끝 이동 → 31–34번 매듭 해제 → 35–37번 단일 띠 → 38–40번 퇴장. 41–45번은 전체 픽셀 alpha=0이다.
- 공개 WebP 46장은 총 3,438,298바이트다. 완전 투명 픽셀의 보이지 않는 RGB만 0으로 정리했으며, 모든 알파와 가시 픽셀 RGB는 원본 PNG와 같다. 정리된 RGBA는 무손실 왕복 일치를 확인했다.
- 공개 자산 검사에서 같은 캔버스, 전체 4MiB 이하, 프레임 표면 추정 17,203,200바이트, 마지막 완전 투명을 확인했다. 브라우저 자체 메모리 비용은 이 추정에 포함하지 않는다.

샘플의 시각 검증을 통과해 공개 앱 통합 단계로 진행했다. 레퍼런스의 촬영 장면을 픽셀 단위로 복제했다는 의미는 아니다.

## 공개 앱 통합: 로컬 검증 통과

`tests/pastel-intro-browser.test.mjs`의 18개 시나리오를 포함해 전체 UI 테스트 113개가 통과했다. 실제 공개 WebP를 사용해 프레임 0–45 순서, 마지막 완전 투명 이후 최소 300ms의 패널 지연, 종료 시 커버·스크롤 잠금 해제와 기존 사진 객체·소스 보존을 확인했다.

정상 Pastel의 360/390/430/768/1440px 재생, 줄인 모션 설정에서도 재생, 새로고침 재생, 두 디자인의 요구 너비, capture·Quiet 예외, 로딩 중 건너뛰기, 요청 실패와 5초 로딩 제한을 검증했다. 각 실제 `innerWidth`를 기대값과 비교했고 저장한 PNG 픽셀 크기도 비교했다. 마지막 화면의 사진과 조상 요소의 computed opacity/display/visibility를 읽었다.

인앱 브라우저에서는 390px 리본 재생과 개봉 후 본문·스크롤 복원을 직접 확인했다. 인앱 브라우저의 1440px 변경 요청이 실제 너비를 바꾸지 않는 한계가 있어, 그 화면을 데스크톱 통과 증거로 사용하지 않았다. 별도 자동 테스트에서 실제 1440px와 초기·최종 PNG를 검증했다.

두 브라우저 테스트의 Vite 서버가 기본 포트에서 충돌하던 문제는 `strictPort:false`로 다음 사용 가능한 포트를 허용해 수정했다. 병렬 전체 테스트도 통과했다.

모바일 실기기의 성능은 아직 확인하지 못했다. 화면 너비를 바꾼 브라우저 테스트를 실기기 검증으로 간주하지 않는다. 배포 완료 판정에는 독립 코드 검토와 보호된 GitHub Actions 배포 후 프로덕션 canary가 추가로 필요하다.

## 배포 검증 보완

GitHub 최종 검토의 RIBBON-P2-1은 기존 렌더 검사가 사진 준비 직후 끝나므로 리본이 누락되어 개봉을 건너뛰어도 통과할 수 있다는 지적이다. 배포 검사에 실제 프레임 순서, 마지막 투명 화면, 종이 개방 지연·완료, 커버 제거와 스크롤 복원 후의 사진 표시 상태를 추가했다. 배포 응답의 manifest와 각 WebP SHA-256은 검증된 빌드 파일과 비교한다.

요청마다 400ms 지연을 추가한 실제 브라우저에서 다운로드 동시성 4는 5초 준비 제한에 걸려 프레임을 그리지 못했다. 동시성을 8로 변경한 동일 조건은 전체 프레임 재생과 본문 복원 검사를 통과했다. 디코딩 동시성 2와 디코딩 캐시 4장 제한은 유지한다. 이 회귀를 포함한 리본 브라우저 검사 20개가 통과했다.

로컬 서버에 게시 bootstrap·Worker 식별 헤더를 주입해 운영과 같은 `collectScenario`를 실제 브라우저에서 실행했다. 새로고침 후 manifest와 프레임의 응답 47개만 기록됐고, 파일 해시·형식·순차 재생·마지막 투명도·개봉 지연·최종 사진 표시 검사가 통과했다. 새로고침 검사는 첫 재생이 끝난 뒤 시작하며 요청 시점의 탐색 번호로 이전 응답을 제외한다. 렌더 canary 검사 28개와 리본 단위 검사 13개가 통과했다. 이는 운영 서버의 배포 후 검사와 별도인 로컬 검증이다.
